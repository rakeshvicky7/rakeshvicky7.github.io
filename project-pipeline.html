Grocery Sales Data Pipeline

Data engineering · PostgreSQL, Spark, Airflow, Docker

Five million grocery sales rows moved from flat files into a handful of tables a dashboard can read instantly — orchestrated end to end, safe to run twice, and fitted inside the 3.7 GB a laptop actually gives Docker. Every performance claim on this page was measured, including the two experiments that produced no improvement.

View the repository

1 · The idea behind the project

Raw sales data answers nothing. A question a retailer actually has — which product family is slowing down, in which store, and did the promotion do anything — needs those rows counted and grouped first. Doing that on demand over five million rows takes minutes. Doing it once, ahead of time, and storing the result takes milliseconds to read.

That is what a batch pipeline is for, and this one carries the work from six source CSV files through to six small analytics tables, with Airflow deciding the order and Docker Compose making the whole stack start with one command.

The table that justifies the rest

The final job builds daily_context — one row per trading day with total units, the number of sales lines, the forward-filled oil price, a national holiday flag and the day of the week. That table is what a downstream machine-learning model reads, and it is the only reason the oil-price and holiday files are ingested at all. A pipeline stage that no reader consumes is cost without purpose.

Why it runs quarterly

The schedule is @quarterly, matching the retraining cadence of the model that consumes the output. A daily schedule would rebuild identical aggregates ninety times over for nobody. Choosing the cadence from the consumer rather than from habit is a small decision that saves most of the compute this project would otherwise spend.

2 · The data, and the decision hidden inside it

The source is a public grocery sales competition dataset — about 5 GB across six files: the sales fact table, plus stores, items, oil prices, holidays and transactions. The sales file alone holds tens of millions of rows, more than this stack should attempt, so the load is capped.

Where exactly that cap starts turned out to matter more than its size.

The file is ordered by date. That sounds harmless until you look at what the columns contain across it.

The promotion column is empty for the first 21.6 million rows. A row cap applied from the beginning of the file would have loaded five million rows in which every promotion flag was blank — and the promotion analysis would have reported a single category, correctly and uselessly.

So the window is moved, not just sized. The load begins at the first date carrying promotion data. The cap decides how much; the start date decides where — and only together do they select a window that can answer the question. The result: promoted lines average 12.96 units against 8.78 for non-promoted.

The unwanted rows still have to be read. They are parsed and discarded at around 420,000 rows a second, in fixed 50,000-row chunks, so memory is bounded by the chunk rather than the file. Altogether 26.6 million rows pass through a process that never holds more than one chunk — which is what makes a 5 GB dataset tractable on a laptop.

Each file is also profiled on ingest, and the validator writes a data-quality report per source rather than silently accepting whatever arrives.

3 · How the work is arranged

Eleven Airflow tasks run in order: validate the CSVs, load the raw schema, then six independent Spark aggregations, then a database backup. Airflow owns sequencing and records what ran, when and with what outcome; the actual work happens in PostgreSQL and Spark.

Ingest. The CSVs are validated and profiled first, then loaded into a raw schema that nothing downstream is allowed to modify. Splitting the work into eleven named tasks rather than one long script means there is no half-succeeded state to reason about afterwards.

Aggregate. Six independent Spark jobs read the raw sales table over JDBC and write small summary tables — by day, by month, by store, by product family, by promotion status, and the combined daily context table. Jobs are submitted to a standalone Spark cluster, so executors run in their own container rather than inside the scheduler.

Back up. A database dump runs last, in PostgreSQL's custom format, so a single artefact holds both the raw data of that run and the analytics built from it.

Who may write what. Spark does not connect as the database owner. It uses a restricted role with read-only access to the raw schema and write access only to analytics. The consequence is worth stating plainly: a mistake in an aggregation job can corrupt an aggregate, which is rebuilt from source anyway, but it cannot touch the ingested data underneath.

The analytics tables are declared, not inferred

Their shape and primary keys live in a SQL file in the repository rather than being created by whatever Spark happened to write. The jobs then write with overwrite-and-truncate, which empties the tables instead of dropping them — so the declarations survive every run, and the schema is something you can read and review rather than something you discover.

4 · Running it twice

Pipelines fail halfway. A container is restarted, a machine runs out of memory, someone re-triggers last quarter's run by accident. The question is never whether that happens — it is what the data looks like afterwards.

The whole DAG was run twice in succession on a stack rebuilt from empty volumes. All eleven tasks succeeded both times, and every row count was identical afterwards.

5 · Measuring it honestly

Three experiments were run. Two produced no improvement, and both changes were kept anyway — for reasons worth more than the numbers.

Running on the cluster is 3.5× slower — on one machine. In local mode the data never leaves the process. On the cluster each job is a separate submission, so each starts a fresh executor and every row crosses a container boundary. The slower configuration was kept, because running on a cluster is what the architecture claims, and five applications registering with the master is the evidence that the claim is real. The cost of distribution is genuine; it just does not pay on a single host.

Splitting the read four ways produced no gain. 354 seconds against 401 — and the difference is inside run-to-run variation on a laptop. Database, driver and executor share one host, one disk and about two cores, so four concurrent scans over the same table add contention rather than bandwidth. The change was still kept, because with one partition the read is a single task that additional workers cannot help with at all. It removes a structural limit rather than a measured one — and the page says exactly that instead of claiming a speed-up.

The earlier load timings were wrong, and finding that out mattered. Previous runs recorded the fact table loading in two to three minutes — but in those runs the rows were already present, so insert-on-conflict discarded nearly every write without doing any work. Against a genuinely empty table, with the primary key and both foreign keys checked per row, the same five million rows take 949 seconds. The mechanism that makes re-runs safe also makes them cheap, and quoting a re-run as the load cost overstates throughput roughly fivefold.

Why publish results that make the system look worse. Because the alternative is a portfolio of numbers nobody can reproduce. One comparison was also deliberately not run — two Spark workers against one — because two executors would have needed about 6.4 GB against the 5 GB available and the run would simply have been killed. Saying so is more useful than a figure produced by an experiment that could not have worked.

6 · Constraints, and what is deliberately not here

The whole stack fits in 3.7 GB

That is what Docker Desktop allocates by default on an 8 GB machine, and it is the budget everything was tuned to. Two settings carry it: the Spark driver is capped at 1500 MB, and the Airflow web server runs one worker instead of four. Raising the driver to 2 GB on a machine this size gets it killed by the operating system partway through a job — and the symptom is an Airflow task exiting with code 137, which is the kernel, not the application. Knowing which of the two failed is the difference between a five-minute fix and an afternoon.

Kafka is present and deliberately not wired in

Topics, a producer and a consumer exist, and the round trip has been exercised: five events published, the same five consumed back. They arrived out of order, which is correct — the topic has three partitions and Kafka orders messages within a partition, not across them. But streaming is not integrated into the batch pipeline, because batch and streaming answer different questions and pretending otherwise would be decoration. On a small machine those containers can simply be stopped to free memory.

Reproducibility was tested, not assumed

The verified run started from a clean clone with empty volumes. There are twelve tests, passing in about eight seconds, and test collection is restricted to the test directory for a specific reason: Airflow creates a symlink from inside its Linux container that Windows cannot follow, and without the restriction collection aborts before a single test runs. Small, but it is the kind of thing that stops a project working on anyone else's machine.

What I would do next

  • Measure worker scaling on a machine that can hold it. The partition experiment was run in its place, and it answers a smaller question.
  • Integrate the streaming path properly, with a clear question it answers that batch cannot.
  • Incremental loading rather than a capped window, so a run processes only what arrived since the last one.
  • Data quality as a gate, not a report. The validator profiles each file; it does not yet stop the pipeline when a source degrades.
